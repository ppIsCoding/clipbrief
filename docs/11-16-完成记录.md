# 11/16 完成记录

> 对应计划：下载进度条、加载/空状态、播放兼容性。
> 本轮把下载从「同步返回文件」改成「任务 + SSE 进度 + 取文件」，并实际验证下载文件能播放。

## 一、后端

### 1. 下载任务接口

| 方法 | 路径 | 作用 |
| --- | --- | --- |
| POST | `/api/download/start` | 创建任务，立即返回 `task_id` |
| GET | `/api/download/progress/{task_id}` | SSE 推送 `pending → downloading → processing → done/error` |
| GET | `/api/download/file/{task_id}` | 文件就绪后取文件，响应结束自动删临时文件 |

- 任务表加锁，任务 15 分钟过期；启动新任务时顺带清理过期任务和残留文件。
- 后台任务用 `BACKGROUND_TASKS` 持有强引用，避免被 GC。
- 旧 `/api/download` 保留，兼容旧调用。

### 2. 进度准确性

yt-dlp 的 `progress_hooks` 在合并档里只给到单条流的信息，直接算百分比会在「视频下完、音频刚开始」时从 99% 掉回 20%。

处理方式：

1. 下载前用同一套参数预解析一次，拿到实际会下载的 `requested_formats`，把各流大小相加作为分母。
2. 进度按累计已下载字节 / 分母计算，封顶 99%。
3. 最后一条流下载完才发 `processing`（正在合并音视频），合并结束后发 `done`。

实测合并档进度点：0.1 → 5.6 → 13.8 → 27.9 → 49.2 → 70.8 → 90.1 → 98.3 → processing → 100，全程单调。

### 3. 播放兼容性

之前默认会选中 AV1 编码（B站 `av01`），文件本身完整，但 Windows 自带播放器可能打不开。现在：

- 解析时同清晰度优先保留 H.264，`label` 显示编码：`1080p MP4 · H.264 (仅视频, 66.6MB)`
- 下载参数加 `format_sort: ["vcodec:h264", "acodec:aac"]`，`bestvideo` 优先选 H.264
- 合并档大小按视频流 + 音频流估算，和实际文件基本一致（71.7MB vs 71.75MB）

### 4. 失败清理

下载异常时按本次任务的 token 删除半成品文件，避免 `backend/downloads` 越积越多。该逻辑已实现，但本轮没有专门制造失败场景验证。

## 二、前端

- `startDownload` → `EventSource` 监听进度 → 进度 100% 后取文件保存。
- 下载按钮实时显示百分比；下方进度条显示「42% · 31.6 MB / 71.7 MB」和速度。
- 后端暂时给不出百分比时（抖音下载），进度条走不确定态动画，不假装有进度。
- 合并阶段显示「正在合并音视频...」。
- 格式列表为空时显示「该视频没有可下载的格式，请换一个链接」。
- 下载过程中禁用格式切换，避免视觉上换了清晰度但实际下载的是旧选择。
- Mock 服务补了 `download/start`、`download/progress`、`download/file`，前端不启后端也能演示进度条。

## 三、验证

### 接口

- `/api/download/start` 返回 `task_id`
- SSE 进度单调，最终 `done`，文件 75,234,063 bytes
- 文件取完后再次请求返回 404，`backend/downloads` 为空

### 页面（Playwright）

- 选 1080p 合并档，进度条从「正在准备下载...」到 98%，再显示「正在合并音视频...」
- 采样 108 个不同的进度文案，速度正常显示
- 下载完成无错误提示条，文件名正确

### 文件播放（ffmpeg 实际解码）

| 检查项 | 结果 |
| --- | --- |
| 容器/编码 | MP4，H.264 1920×1080 + AAC 48kHz 双声道 |
| 时长 | 212.3 秒，与源视频一致 |
| 完整性 | `ffmpeg -v error -i file -f null -` 退出码 0，无解码错误 |
| 画面 | 10s / 1:40 / 3:20 抽帧，画面内容正常 |
| 声音 | `volumedetect` 平均 -16.9 dB，最大 -0.8 dB，不是静音 |

结论：下载的合并文件可以直接播放，音画都有。
